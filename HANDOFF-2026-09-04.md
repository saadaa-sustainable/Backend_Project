## Halo semantics (product decision)
For every SKU in a **mixed basket** (2+ distinct master SKUs) that came from Meta-family traffic:
- `halo_units` += (order_total_qty) − (this SKU's qty)
- `halo_revenue` += (order_total_revenue) − (this SKU's line_revenue)
- `halo_orders` += 1
- `halo_spend` intentionally stays 0 (ad_spend is already fully distributed across the basket via `ad_spend`/`ad_spend_vw`; charging halo_spend on top would double-count)

Symmetric across the basket — basket `{SMCP ₹700, SMFLK ₹300}` gives SMCP halo=₹300 and SMFLK halo=₹700.

30-day figures on 2026-09-04: 71 SKUs have halo activity, ~9.8k halo_units / ₹91L halo_revenue. Rider SKUs like SDASK show halo % = 149% (halo exceeds attributed rev), which is the intended signal.

## Cron infrastructure
Both `.github/workflows/daily-refresh.yml` files have this shape:
```yaml
on:
  workflow_dispatch:
    inputs: {skip_meta, only_silver}
  # schedule:
  #   - cron: "30 19 * * *"   # CTD  → 01:00 IST
  #   - cron: "30 23 * * *"   # BP   → 05:00 IST  (in the BP file)
```

`cron_run_log` schema: `(id, project, run_started, run_finished, duration_s, status, workflow_run, git_sha, steps jsonb, n_steps_ok, n_steps_fail, error, host)`. Wrapped via `utils/cron_log.py` context manager — every subprocess step gets a row in `steps` jsonb with `{status, duration_s, error}`.

Check status any time:
```

./.venv/Scripts/python.exe scripts/check_cron_status.py --limit 5 --show-steps
```
